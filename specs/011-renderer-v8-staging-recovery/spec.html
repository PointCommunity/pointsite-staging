Staging Renderer v8 Recovery

Assumptions

  1. Resolving the request authorizes a staging-only branch, pull request, merge, and deployment verification.
  2. The published revision 83 content and uploaded media are intentional and must be preserved.
  3. Builder Issue #22 and its dirty worktree are unrelated and must not be changed.

Objective

Restore both PointSite staging GitHub Actions workflows by making the committed staging renderer compatible with the already-published schema-v8 candidate, while adding an early regression test for future renderer/content drift and preserving accessible responsive navigation.

Tech stack and structure

Node.js 22, TypeScript, Next.js 16 static export, React 19, Zod, Node test runner, Playwright, and Cloudflare Workers. Shared runtime files live in site-kit/; the staged candidate lives in content/; staging-only compatibility rules live in app/staging-overrides.css; checks live in tests/; synchronization lives in scripts/.

Commands

Focused test: npm test -- --test-name-pattern="matches the committed renderer contract"
Unit/contract tests: npm test
Lint and build: npm run check
Static verification: npm run verify:staging
Browser acceptance: npm run test:e2e
Diff validation: git diff --check

Code style

test("published candidate matches the committed renderer contract", async () => {
  assert.equal(document.schemaVersion, RENDERER_IDENTITY.schemaVersion);
  assert.equal(document.rendererVersion, RENDERER_IDENTITY.rendererVersion);
});

Follow the repository’s existing TypeScript, Node test runner, strict Zod, and single-quote formatting conventions.

Testing strategy

First add a focused contract test and prove it fails on the broken v5-renderer/v8-content commit. Then sync the exact v8 site-kit from clean Builder origin/main, rerun the focused test, and execute browser tests. Treat schema incompatibility, invalid media-aware checksum assertions, inaccessible inherited navigation color, and obsolete pixel equality against intentionally edited staging content as separate root causes. Finish with the repository’s complete local workflow-equivalent checks and exact-head GitHub workflows.

Boundaries

  • Always: preserve revision 83 content/media, use exact clean upstream renderer files, and verify both Quality and Deploy staging.
  • Ask first: production PointSite publication, Builder application changes, authentication changes, or destructive recovery.
  • Never: include private Builder credentials/data, overwrite unrelated dirty worktrees, push to the production remote, or weaken schema validation.

Success criteria

  • The v8 candidate parses with the committed v8 schema and renderer identity.
  • The sync inventory includes all runtime dependencies introduced in v6-v8.
  • Primary-surface navigation inherits the section’s accessible foreground color, and responsive navigation remains operable independent of its editor-configurable accessible label.
  • The staging candidate may differ intentionally from current production content while both retain the same route and responsive-layout coverage.
  • Local tests, lint, static build, staging verification, browser acceptance, audit, and diff checks pass.
  • Both GitHub workflows pass for the exact merged staging commit and protected staging routes verify.

Open questions

None blocking. A Builder-side preflight that rejects future renderer drift is desirable but belongs to a separate Builder issue because Issue #22 is currently active.
